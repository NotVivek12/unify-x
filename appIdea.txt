# UNIFY-X — End User App Specification

## 1. What the app actually does

The app is the **end-user interface for the UNIFY-X transport monitoring system**.

The user should NOT need to understand:

* MQ135
* MQ137
* BME688
* machine-learning algorithms
* feature extraction
* model training
* Raspberry Pi processing

The Raspberry Pi handles all of that.

The app's job is to answer five simple questions:

> **What am I transporting?**
> **Where is it?**
> **How is the shipment doing right now?**
> **Is the product still good?**
> **Has anything gone wrong during transportation?**

So the app should be designed around **shipments**, not around sensors.

# 16. Don't spam notifications

Only send notifications for:

### Critical

* BAD classification
* Sensor failure
* Raspberry Pi offline
* prolonged temperature excursion

### Warning

* unusual gas trend
* temperature approaching threshold
* model uncertainty

Don't notify the user every time temperature changes by 0.1°C.

# 18. The app should communicate with APIs

Tell your friend:

**Do NOT access the Pi's CSV files directly.**

The Pi should expose APIs.

Suggested API structure:

```text
GET  /api/system/status

GET  /api/shipments
GET  /api/shipments/{id}

GET  /api/shipments/{id}/live
GET  /api/shipments/{id}/history
GET  /api/shipments/{id}/analysis

GET  /api/alerts

POST /api/shipments/{id}/start
POST /api/shipments/{id}/stop
```

For live data:

```text
WebSocket
/ws/live/{shipment_id}
```

Your current Pi already runs an HTTP server, so this is a natural evolution of the existing architecture.

# 20. What happens when a detection is performed

The complete user flow should be:

```text
Shipment arrives
       ↓
RFID identified
       ↓
Nodes start collecting data
       ↓
Pi receives sensor data
       ↓
Pi synchronizes both nodes
       ↓
Feature extraction
       ↓
ML models
       ↓
Decision engine
       ↓
GOOD / BAD / UNCERTAIN
       ↓
Result stored
       ↓
App receives update
       ↓
User sees result
       ↓
Transport history updated
```

The end user should see this as:

```text
Scanning...
     ↓
Analyzing...
     ↓
😊 GOOD
92% confidence
```

Not all the backend complexity.

# Message you can directly send your friend

> **UNIFY-X APP — DEVELOPMENT BRIEF**
>
> The app is the end-user layer of a Raspberry-Pi-based edge-AI transport monitoring system. The Raspberry Pi is the central intelligence/server. It receives data from two sensor nodes, performs data fusion, feature extraction, ML inference and the final GOOD/BAD/UNCERTAIN decision.
>
> The app must NOT perform ML computation or directly access sensor CSV files. It communicates with the Raspberry Pi through REST APIs and WebSocket for real-time updates.
>
> The app should be **shipment-centric, not sensor-centric**.
>
> **Primary user questions:**
>
> 1. What shipment am I monitoring?
> 2. Where is it / what is its transport status?
> 3. What is its current condition?
> 4. Is it GOOD, BAD or UNCERTAIN?
> 5. Why did the system make that decision?
> 6. Has anything abnormal happened during transportation?
>
> **Main navigation:** Home / Shipments / Alerts / More.
>
> **Home:** Active shipment, product, origin/destination, transport duration, current GOOD/BAD/UNCERTAIN decision, confidence/risk score, sensor summary, temperature excursion summary and system connectivity.
>
> **Shipment Details:** Overview, live sensor monitoring, temperature/gas trends, transport timeline, abnormal events, model consensus and final decision.
>
> **Alerts:** BAD product classifications, temperature excursions, unusual gas trends, sensor failures and Raspberry Pi/node connectivity problems.
>
> **Backend API:** REST for shipment/history/status data and WebSocket for live sensor/status updates.
>
> **Important:** Raspberry Pi is the single source of truth for the final product classification. Node displays and mobile app only reflect the Pi's decision.
>
> **Core states:** CONNECTED, OFFLINE, SCANNING, PROCESSING, GOOD, BAD, UNCERTAIN, SENSOR ERROR, MODEL NOT READY.
>
> The design should feel like an **industrial cold-chain/logistics monitoring application**, not an IoT sensor demo. The most important information on the Home screen is the current shipment and its final product condition.

### One final recommendation

**Before your friend writes the UI, you and the ML/backend person should freeze the JSON/API contract first.** That's the interface between your two teams. Once that contract is stable, your friend can build the entire UI using mock JSON even while you're still integrating BME688, MQ sensors, the second node, and the ML models. That will let both sides work **in parallel during your six-hour window** instead of waiting for each other.
